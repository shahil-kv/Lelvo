# Upload, retry, queue and background runs: Lelvo vs Ente vs Immich

Method: closed-issue mining (GitHub search was rate-limited after the first calls, so issues were listed with `gh issue list` and read with `gh issue view`), then the code that implements the fixes. Clones are shallow (1 commit), so fix history (git log) was not available; fixes are cited from issue comments. Line numbers are from the clones/repo on 2026-11-18.

## How Ente does it

Single Dart `FileUploader` with a queue and up to 4 concurrent uploads (`mobile/apps/photos/lib/module/upload/service/file_uploader.dart:52`). Every file takes a row lock in SQLite (`db/upload_locks_db.dart`, `tryAcquireLock` at file_uploader.dart:403) so the foreground app and the background isolate never upload the same file; a lock owned by the other process raises `LockAlreadyAcquiredError`, and the foreground moves the item to the background queue (:268). On start, locks owned by this process type are released, any lock older than 4 hours is released (`kSafeBufferForLockExpiry` :73, :98-:110), and foreground clears background locks only when the background engine is dead (:112). Errors are classified: `StorageLimitExceededError`, `NoActiveSubscriptionError`, `FileTooLargeForPlanError`, `InvalidFileError` are hard failures that clear the queue or ignore the file (:787-:803); `isDeviceStorageFullError` stops sync and clears the queue (:271-:277); HTTP 429 pauses the queue 5 s (:283). A free-space-on-account preflight runs before encrypting (:885-:915). Unrecoverable files go to an ignored-files table (`_onInvalidFileError` :921, `db/ignored_files_db.dart`). Multipart uploads persist a track so they resume, and the track is deleted on PUT errors (:440, :807). Temp copies are cleaned (`upload_artifact_lifecycle.dart`). Issues: [#10031](https://github.com/ente-io/ente/issues/10031) silent slow failure when device full, [#10055](https://github.com/ente-io/ente/issues/10055) iCloud temp copies fill the disk (fixed by PR #11276), [#14325](https://github.com/ente-io/ente/issues/14325) lock error on add-to-album during backup, [#13746](https://github.com/ente-io/ente/issues/13746) one malformed record wedged sync (maintainers kept it "by design"), [#14455](https://github.com/ente-io/ente/issues/14455) videos with errors retry forever on S3.

## How Immich does it

Two paths. Foreground (`mobile/lib/services/foreground_upload.service.dart`): worker pool of 3 (`_executeWithWorkerPool` :205-:238), sequential in the background isolate (:116), shared `Completer` cancel token checked per item (:127, :217), skips non-Wi-Fi items when only metered (:105-:111). iCloud-only assets are downloaded with a progress handler (:264-:317) and the temp file is deleted in `finally` on iOS (:411-:423). Quota error aborts the whole run (:404); every other error is reported per asset and the run continues. Background path (`background_upload.service.dart:399-:453`) hands uploads to the OS via the `background_downloader` task library: `requiresWiFi`, `priority`, `retries: 3`, so the OS owns resume and survival. Dedup is by SHA-1 checksum: server returns DUPLICATE with the existing id (`server/src/services/asset-media.service.ts:218-:231`), and a bulk pre-check endpoint (:322-:339); hashing is batched and cancellable (`hash.service.dart:96-:125`). Issues: [#30458](https://github.com/immich-app/immich/issues/30458) unreadable local assets retry forever with no way to clear them, [#20331](https://github.com/immich-app/immich/issues/20331) iCloud assets re-queued after upgrade (9000 "left to upload"), [#14165](https://github.com/immich-app/immich/issues/14165) deleting on the server makes the next scan re-upload, [#28602](https://github.com/immich-app/immich/issues/28602) and [#31722](https://github.com/immich-app/immich/issues/31722) iOS export returns a reduced/different original than Photos, [#20408](https://github.com/immich-app/immich/issues/20408) large temp storage during iOS backup.

## How Lelvo does it

One in-process engine per platform. iOS/Mac: `Shared/Services/BackupEngine.swift` `run()` (:557) claims a `running` flag under a lock (:590-:597), starts two lanes (`maxConcurrentUploads`, loop :640-:700) with a shared upload-slot counter and start pacing (`acquireLaneSlot` :162, `paceUploadStart` :222). Every send waits for `FLOOD_WAIT`, which is persisted across launches (`pausedUntil` backed by `Prefs.floodUntil` :249, `holdForFlood` :239); a flood is a state change that does not count an attempt (`JobMachine` `JobQueue.swift:56-:60`). Retry policy: transient errors back off 5 s doubling to 30 min, max 5 attempts, then `.failed` (`JobQueue.swift:39-:68`); failed rows are retried only by the explicit Retry button (`retryFailed` :793, callers `BackupDashboardView.swift:186`, `MacBackupView.swift:201`), not by automatic or "Back up now" runs. Nothing counts as backed up until every part is confirmed with the expected size (`CloudUploader.swift:126-:131`, `sent(true)` -> `.verified`). Parts are resumable (`CloudUploader.swift:69`), the work dir is removed in `defer` (:51). Network blips wait up to 2 minutes instead of ending the run (`waitForConditions` :803). A stall watchdog (`UploadStall.swift`, 180 s, suspend-aware; `TDService.swift:636`) turns a dead TDLib send into a transient error. A `RunHeartbeat` (`RunHeartbeat.swift`) detects a run iOS froze and lets a new run take over (`stopFrozenRun` :270, `run` :593-:595). Killed-process runs are recorded (`BackgroundRuns.swift:41-:60`). Background: BGProcessing (power/network flags, `BackgroundTasks.swift:50-:62`), BGAppRefresh as short run with a deadline 8 s early (`BackupEngine.swift:625`), iOS 26 continued processing, expiration handlers set a cancel flag (:74, :100). Free-space preflight before export (`checkFreeSpace` :331, throws permanent `NotEnoughSpaceError`). Android: `android/data/.../backup/BackupEngine.kt` mirrors the same design (run :361, gate `running` :368, queueLock :401, persisted `floodUntil` :156/:592, stale `Uploading` rows reset to queue :390, classifier :992-:1014), driven by WorkManager unique work with a foreground service (`BackupWorker.kt:266`, `BackupScheduler.kt:55`).

Gap check of the four already-known gaps:
1. Run does not halt on session-revoked / channel-wide permanent errors: CONFIRMED. `fail()` maps `.auth`/`.permanent` to a per-item `.failed` (BackupEngine.swift:1584-1586) and the lane loop only reacts to cancel, deadline, and conditions (:654-:672). Every remaining item will hit the same error and be marked failed one by one (a revoked session burns all queued items to `.failed`, forcing manual Retry). Android `fail` :1014 same shape.
2. Device-disk-full from the OS treated as transient: CONFIRMED. `fail()` falls to `.transient` for any non-TD, non-listed error (:1577); an `NSFileWriteOutOfSpaceError` or ENOSPC during export/part write is retried up to 5 times each item. The preflight only protects the common case (estimate + margin). Android has the same default (no IOException/ENOSPC branch, BackupEngine.kt:1002).
3. Permanently failing files retried by every manual run: REFUTED as stated. `runnableItems` selects only `.queued`/`.uploading` (:548); `.failed` rows wait for the Retry button. Real residual gap: Retry re-queues all failed rows and re-fails the same unreadable ones with attempts reset to 0, and there is no "ignore this file" state like Ente's ignored-files table or a way to clear it (Immich #30458).
4. Stale lock / overlapping background vs foreground: MOSTLY REFUTED on iOS/Mac/Android because there is one process and one `running` flag (:590, Kt:368), so no cross-process lock is needed; the frozen-run takeover covers the stale-flag case. Residual risk: App Intents/extension processes on iOS (`BackupIntents.swift`) and any second Android process would not share the flag; not verified whether the intents run in-process.

## Pillars

UI: Lelvo shows per-lane progress, stop reasons and a Retry button; Ente/Immich show per-asset errors, Immich iCloud progress. Missing in Lelvo: an Ignore action and an explicit "sign-in needed" banner when auth fails. UX: Lelvo's wait-and-resume on blips and persisted FLOOD_WAIT are better than either; failure messaging for hard stops (revoked session, disk full) is weaker. Performance: two lanes, no whole-library reads in the run (Android ids only); Ente runs 4, Immich 3, but Telegram caps us at 2. Edge cases: both competitors fixed disk-full, ignore list, iCloud temp leakage; Lelvo lacks the first two as run-level halts.
